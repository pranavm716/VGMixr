# VGMixr roadmap

One step per Claude Code session. Run `/clear` between steps. Phase 0 commits go directly to `main`. From step 1 on, each step gets its own branch, is test-first, ends green, and is merged into `main`. Check a step off on its own branch, as the last commit before the merge, so `main` never shows a merged step unchecked.

## Phase 0: manual setup (not a Claude Code session)
- [x] Create the Android project (Empty Activity, Compose, Kotlin), run it once, commit.
- [x] Add `.claude/` files, CI workflow, `.gitattributes`, `scripts/check-forbidden-files.sh`. The Stop hook and CI start with the checks that exist today (`assembleDebug`, `testDebugUnitTest`, `lint`); `pytest` runs only if `pipeline/` exists. Confirm those Gradle commands work.

8. [x] Playback core with streams: remote tracks play end to end, in the background with a notification, tested with fakes. Highest-risk step, so it starts with a spike: resolve one video id with NewPipe and play it on the phone, plus a slice of the SV album video.
    - Streams first: `StreamResolver` (domain) with a NewPipe Extractor implementation in `data/` and a fake for tests. The resolver tells "video gone" (try the next stream source) from "network down" (stop and show an error). NewPipe needs Java NIO APIs that Android has only from API 33, so the app turns on core library desugaring (`desugar_jdk_libs_nio`); its downloader uses `HttpURLConnection`, no OkHttp.
    - `PlaybackController` (domain) with a Media3 implementation: a `MediaSessionService` for background playback and the notification, driven through a `MediaController`. Queue items carry the track id and resolve to a stream URL only when they play (a `ResolvingDataSource`), since URLs expire. `startMs`/`endMs` slices play through clipping. A source that fails moves on to the track's next stream source, then skips the track.
    - Local files wait for the rips (see the local file playback candidate): until then every `local` source counts as missing, the existing skip rule, so Route 101 plays its stream.
    - A two-tier queue, as Spotify's: tracks the user adds ("Next in queue") play right after the current one, ahead of the rest of what was tapped ("Next from <family>"). Tapping a track plays its family's list from it; the earlier tracks stay behind it so "previous" walks back, and the tracks waiting in the queue stay right after it (queued tracks already played are dropped). Swipe to queue adds to the end of "Next in queue"; with nothing to play (empty queue, or playback ended) the added tracks start playing, since nothing else would show they were added. The rules live in a pure domain `PlayQueue`; Media3 keeps one playlist laid out as `[earlier…, current, queued…, rest of the family…]`, each item flagged as queued in its request metadata. Step 9's now-playing shows the two sections.
    - The family screen shows the current track, as Shuttle does: its row is tinted with the accent (12% over the background), its number turns into a small accent spinner while its stream loads, and opening a family whose track is playing scrolls that row to the middle of the screen, once (coming back keeps the user's scroll).
    - Swipe to queue: a swipe right on a family row (all its tracks, in family order) or a track row adds to the end of "Next in queue", as Spotify's "Add to queue". One shared wrapper, `SwipeToQueue(onQueue) { row }` in `ui/components/`, a plain horizontal drag (Material's `SwipeToDismissBox` slides the row fully off before springing back): the row uncovers the accent with a white queue icon 24dp in, stops once its left edge is as far past the icon as the icon is from the screen edge (72dp), with a haptic tick, and springs straight back on release. Letting go there adds to the queue; letting go short of it, or after dragging back, doesn't. A confirmation snackbar ("Added 107 tracks to queue") and an "Add to queue" accessibility action. Rows stay separate composables and only emit a queue event; the ViewModel resolves it to track ids (`Catalog.filter`) and enqueues them through `PlaybackController`. A swipe that starts at the screen's left edge is Android's back gesture instead; rows start 16dp in.

A tap on the mini player, a track or the notification opens it, and back closes it, at an easier 500 ms. A placeholder until part 2.

Each queue item carries its context, as it carries the queued flag. Only families exist yet; playlists and YouTube tracks plug in later without changing now playing.
9b. [x] Remove track categories. Two in five tracks were "Other", the rest mostly guessed from titles, and accurate ones would mean listening to every track; titles already name the context ("Battle!", "Route 101"), so search covers what a category filter would. Decided:

10. [x] Broken marking and source display: a stream source that resolves but fails to play is marked broken in Room (keyed by `videoId`) and skipped from then on. The app says so where the user taps, not on now playing (a sources section there was judged too intrusive):
    - A snackbar when a source fails for the first time: "Skipped <title>: YouTube won't give the app its audio" (or "its video is unavailable", or "its stream didn't play" for an unmarked failure such as a 403), or "Playing another upload of <title>" when a later source plays. Never for a source that was already marked.
    - A track whose sources are all broken is greyed, with a music-off mark at its end, in the family list and the queue. A tap on it plays nothing and shows a snackbar on every tap ("<title> can't play: …") with Try again, which looks the track's videos up again and un-greys it only if one works now ("… can play again"; otherwise the same snackbar, or "Couldn't check … right now" without a connection). Greyed tracks stay out of playback: a tap plays the family list without them, and they can't be swiped to the queue.
    - Fail fast: a source that resolves to no playable audio (YouTube refuses the video to the extractor's client) or is unavailable is not retried by the player's load-error policy, so a dead track is skipped in about a second instead of about eight (four retries). A refused stream URL (HTTP 403) keeps its one fresh retry from step 9.
    - Why it matters now: since PO-token enforcement, YouTube refuses some public videos to every token-free client (found on ORAS in step 9: NewPipe's visionOS client and yt-dlp's android, android_vr, tv, web_safari and web_embedded all refuse them; a browser plays them). Broken marking covers this until the ROM rips (step 20) replace those families' streams; the long-term source for the Switch families, which have no rips planned, is still open (downloads with a token provider, or a WebView PO-token provider for NewPipe).
    - Broken sources reach the PC: the broken marks (track id, `videoId`, reason, an optional free-text detail, when, and the catalog's `generatedAt`; format in `docs/broken.md`, with a shared fixture both sides test against) are kept in Room and mirrored to `broken.json` in the app's external files folder, next to `playback.log`; a pipeline command pulls it over adb into `pipeline/out/`. Marks for videos a newer catalog no longer uses are cleared after its import.
    - Decided, what marks: only `no-audio` (resolves without a playable audio stream, which is how YouTube's refusal to the extractor's client shows; a refusal can't be told apart from a video without audio, so 10b's re-check does that) and `unavailable` (removed, private, restricted). A 403 after the fresh retry, other player errors, and network, bot-check or extractor failures never mark: 403s come and go, and one album video backs a whole family (SV, SM/USUM), so a mark per `videoId` would silence it. The player doesn't retry a refused URL as is either, only the app's retry with a fresh one.
    - Decided, what clears a mark: a newer catalog whose active tracks no longer use the video, or Try again on the snackbar of a greyed track, once the video resolves again. Marks don't expire; a repeated failure keeps the first mark.
10b. [x] Review tool: broken sources. A Broken tab lists the tracks whose sources the app reported (from the pulled `broken.json`), with the reason and when. Each reported video is re-checked the way the app sees it (yt-dlp with the client NewPipe uses), since the tool's embedded browser player plays videos the app is refused; the tab says "gone for everyone" or "refused to the app, plays in a browser". The fix uses the existing tools (reject, search or paste a replacement, add a playlist), then Rebuild; the fixed manifest reaches the phone with the next APK.
    - Decided, the re-check: yt-dlp's `visionos` player client is NewPipe's own client (same name, id 101 and version 1.02), run over IPv4 like the app. On the 4 ORAS marks it returns the watch page's title and "This video is not available" with no audio (refused); on ORAS videos the app plays it returns audio formats; on removed videos "Video unavailable" and no title (gone). Results are cached per video in `pipeline/out/youtube/app-check/` and YouTube is asked only on a click, 5 s apart, under the tool's bot-check cooldown.
    - Decided, reports and tracks: a report finds its track by catalog id (the titles as last built, then today's), else by the draft track using its video. Reports are grouped "needs a fix" (a draft track still uses the video) and "fixed in the draft"; one made on an older catalog is tagged, since its mark stays until a catalog drops the video. `broken.json`'s format is unchanged.
    - Decided, replacements: every source and candidate in the track view gets the same App check, on request. On ORAS another upload from the same channel is refused too, so a replacement is checked before it's accepted.
11. [x] Search tab: offline search over the Room catalog, with fuzzy matching and a ranking that history refines from step 12b on.
    - Decided, the screen: tapping the Search tab (or tapping it again) focuses the field with the keyboard. The field is the top bar: a search icon on its left, a clear button on its right. Results come once typing pauses for 150 ms (as Spotify does; a list per keystroke flashed, and animating the changes was too busy); an emptied field clears at once. Nothing shows under an empty field: no recent searches and no recently played (playlists on shuffle are the main way to listen). One ranked list, rows as the queue's (the family's tile, the title over all of its game chips, the playing track tinted), swipe right to queue. A query that matches nothing says so. Back with the keyboard up only hides it; dragging the results hides it too. The search starts empty each time the tab is opened.
    - Decided, a tap plays the track's family from it, as in the family list ("Playing from <family>"). Greyed tracks are found and shown greyed; a tap says why it can't play. Retired tracks aren't in the catalog, so search never finds them.
    - Matching: the query and each track's title, family id and label, game names and short names, generation and region are lower-cased, stripped of accents ("pokemon" finds "Pokémon") and punctuation, and split into words ("gen 4" is one word; it replaces the generation filter postponed from step 7). Every query word must match a word: whole, as a prefix ("litt" finds Littleroot Town), or within one typo for words of 4 to 7 letters, two for longer ones ("eliet", "centre"; a swap of neighbouring letters is one). Words with a digit never match by typo ("rt 101" doesn't find Route 110). A short alias table in `domain/search/` ("e4" elite four, "vs" battle, "rt" route, "pc" Pokémon Center, "b2w2", "usum") adds to the family ids and labels ("oras", "hgss"). Each family has its main region ("hoenn", "sinnoh"; Legends: Arceus is both "hisui" and "sinnoh"; X/Y and Z-A are "kalos").
    - Ranking: whole and alias matches score 1, prefixes 0.8, one typo 0.6, two 0.4; a title word counts double a family, game, generation or region word, so a title match outranks one. Same scores are ordered by the history hook (`HistoryWeight`, no effect in this step), then by how much of the title matched ("Route 101" before "Pokégear Radio: Route 101"), then in Games tab order. The hook only orders equal text scores, so it never lifts a weaker match.
    - History starts here: a visit to a track counts as a play once it has played 10 s, or at its end for a shorter track (`PlayCounter`); a skip before that, or before its audio starts, doesn't count, and neither does a restart within the visit. The playback service writes it to `PlayHistory` (track id, when; injected clock), so step 12b ranks on weeks of real plays. The table existed since schema 1, so no migration.
    - Plain Kotlin in `domain/` (`search(query, index, history, now, weight)`), unit-tested on hard queries ("pokemon centre", "eliet four", "oras e4", "rt 101", "gen 4 route", regions). About 2,000 tracks are scored in memory per search, 3-13 ms on the phone, off the main thread; no index, no search library. Step 13b's user tracks join the results when they exist.
    - Also in this step: the media notification's artwork is the track's game colors as a left-to-right gradient (`NotificationArtwork`), since families have no covers yet. They are full strength: at the app's 25% over its dark background (the mini player, the family header and now playing) the system turned them into a muddy brown. Android 13+ draws the notification itself from the media session, so artwork, text, buttons and the status bar icon are all an app can style; the system colors the player from the artwork. Covers replace the gradient when they exist; shuffle and favorite buttons come in step 12c.
    - Not now: search by description ("the spooky tower music") needs a language model on the phone or pipeline-written descriptions; a candidate for later.

A row tap doesn't play; the keyboard comes up only when the field is tapped. No recently played or family list. 12b. [ ] History in search ranking: no Recently played section; `PlayHistory` (written since step 11) fills search's ranking hook (`HistoryWeight`, which orders only tracks with the same text score), frecency style (as Firefox's address bar): each play adds to a track's weight, older plays count less (e.g. halved every two weeks), tracks in a playlist or favorites (step 12) get a fixed bonus, which works before any history exists, and the family playing or last browsed lifts a little. It mostly decides between same-named tracks ("Pokémon Center", "Route 101" across families). Tuned on the plays recorded since step 11.
12c. [ ] Shuffle and notification buttons. Shuffle isn't built yet, though playlists on shuffle are the main way to listen: a shuffle toggle on now playing, as Spotify's (it shuffles "Next from", the family or playlist, while "Next in queue" keeps its order; turning it off goes back to list order from the current track; whether it stays on across launches is decided in the step). The media notification gets two custom buttons (Media3's media button preferences): shuffle, and favorite (step 12's toggle).
12d. [ ] Back up user data (minimal): copy the app's Room database between the phone and the PC over adb, so playlists survive an uninstall, a cleared app or a new phone. Updates, Android Studio's Run and new catalogs already keep them; the likely risk is Android Studio's "uninstall and reinstall?" prompt after a signing-key change (keep `~/.android/debug.keystore` backed up). A script with `pull` and `push`: `pull` copies `vgmixr.db` with its `-wal` and `-shm` files (`adb exec-out run-as io.github.pranavm716.vgmixr cat databases/<file>`) into a dated folder on the PC, so recent changes still in the WAL file come along; `push` stops the app, writes the three files back (`adb exec-in run-as … sh -c 'cat > databases/<file>'`) and deletes a `-wal`/`-shm` the backup lacks. Limits: `run-as` needs a debuggable (debug) build on the phone, not a release APK; a backup restores into the same or a newer app version (Room migrates it up), not an older one; a copy taken while the app writes (a play being recorded) can be a moment stale, so stop the app first when nothing plays. Decided in the step: where backups live (committed or gitignored).
13. [ ] Downloads and cache: offline playback, auto-cache favorites and recently played tracks, prefetch the next track. Cache keyed by `(videoId, startMs, endMs)`. Don't auto-cache or prefetch a stream for a track whose local file is present and playable. SV and SM/USUM play slices of multi-hour full-album videos (see step 17): a per-slice cache entry would mean downloading a whole album (a few hundred MB) for one favorite, so decide here between a whole-video cache tier keyed by `videoId` (one download per album, slices clipped from it; Wi-Fi only) and turning those slices into local files first (see the Candidates).
13b. [ ] Add from YouTube (moved forward from v3+): paste a YouTube link to add a track, mainly fan remixes. A `UserTrack` table (`yt:<videoId>` id, video id, optional slice, title, channel, duration, when added, optional `remixOf` catalog track id, so a remix shows its original game's chips and color and links back to it). One lookup per add; no in-app YouTube search for now (bursts of requests risk the bot check). The playback service builds items from `UserTrack` as well as the catalog; user tracks cache, queue and go into playlists like any track. The Add from YouTube tab lists them as a collection you can play from. The manifest is unchanged.
14. [ ] Robustness pass: error and offline states, retired tracks and games shown as unavailable, `/code-review`, CLAUDE.md update.
15. [ ] Visual polish: theme, navigation, icon, using the screenshot loop.

## Phase 3: real catalog (independent of the app; can run in a separate worktree alongside Phase 2)
16. [x] Catalog builder, part A: Bulbapedia track lists into a draft manifest. Decisions:
    - Scope: mainline Gen 1-9, including remakes and both Legends games; no spin-offs.
    - Games come from a hand-written, committed games file (`pipeline/data/games.json`: name, shortName, color, generation, platform, family, and later the YouTube playlists per game). Claude drafts colors (Bulbapedia's version colors) and short names; the user reviews them. Bulbapedia supplies only tracks.
    - Track lists come from Bulbapedia's soundtrack album pages, selected per family as page + disc + optional CD number range in the games file.
