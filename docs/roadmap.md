# VGMixr roadmap

One step per Claude Code session. Run `/clear` between steps. Phase 0 commits go directly to `main`. From step 1 on, each step gets its own branch, is test-first, ends green, and is merged into `main`. Check a step off on its own branch, as the last commit before the merge, so `main` never shows a merged step unchecked.

## Phase 0: manual setup (not a Claude Code session)
- [x] Create the Android project (Empty Activity, Compose, Kotlin), run it once, commit.
- [x] Add `.claude/` files, CI workflow, `.gitattributes`, `scripts/check-forbidden-files.sh`. The Stop hook and CI start with the checks that exist today (`assembleDebug`, `testDebugUnitTest`, `lint`); `pytest` runs only if `pipeline/` exists. Confirm those Gradle commands work.

8. [ ] Playback core with streams: remote tracks play end to end, in the background with a notification, tested with fakes. Highest-risk step, so it starts with a spike: resolve one video id with NewPipe and play it on the phone, plus a slice of the SV album video.
    - Streams first: `StreamResolver` (domain) with a NewPipe Extractor implementation in `data/` and a fake for tests. The resolver tells "video gone" (try the next stream source) from "network down" (stop and show an error). NewPipe needs Java NIO APIs that Android has only from API 33, so the app turns on core library desugaring (`desugar_jdk_libs_nio`); its downloader uses `HttpURLConnection`, no OkHttp.
    - `PlaybackController` (domain) with a Media3 implementation: a `MediaSessionService` for background playback and the notification, driven through a `MediaController`. Queue items carry the track id and resolve to a stream URL only when they play (a `ResolvingDataSource`), since URLs expire. `startMs`/`endMs` slices play through clipping. A source that fails moves on to the track's next stream source, then skips the track.
    - Local files wait for the rips (see the local file playback candidate): until then every `local` source counts as missing, the existing skip rule, so Route 101 plays its stream.
    - A two-tier queue, as Spotify's: tracks the user adds ("Next in queue") play right after the current one, ahead of the rest of what was tapped ("Next from <family>"). Tapping a track plays its family's list from it; the earlier tracks stay behind it so "previous" walks back, and the tracks waiting in the queue stay right after it (queued tracks already played are dropped). Swipe to queue adds to the end of "Next in queue"; with nothing to play (empty queue, or playback ended) the added tracks start playing, since nothing else would show they were added. The rules live in a pure domain `PlayQueue`; Media3 keeps one playlist laid out as `[earlier…, current, queued…, rest of the family…]`, each item flagged as queued in its request metadata. Step 9's now-playing shows the two sections.
    - The family screen shows the current track, as Shuttle does: its row is tinted with the accent (12% over the background), its number turns into a small accent spinner while its stream loads, and opening a family whose track is playing scrolls that row to the middle of the screen, once (coming back keeps the user's scroll).
    - Swipe to queue: a swipe right on a family row (all its tracks, in family order) or a track row adds to the end of "Next in queue", as Spotify's "Add to queue". One shared wrapper, `SwipeToQueue(onQueue) { row }` in `ui/components/`, a plain horizontal drag (Material's `SwipeToDismissBox` slides the row fully off before springing back): the row uncovers the accent with a white queue icon 24dp in, queues the moment its left edge is as far past the icon as the icon is from the screen edge (72dp), stops there with a haptic tick, and springs straight back on release. A confirmation snackbar ("Added 107 tracks to queue") and an "Add to queue" accessibility action. Rows stay separate composables and only emit a queue event; the ViewModel resolves it to track ids (`Catalog.filter`) and enqueues them through `PlaybackController`. A swipe that starts at the screen's left edge is Android's back gesture instead; rows start 16dp in.

## Phase 3: real catalog (independent of the app; can run in a separate worktree alongside Phase 2)
16. [x] Catalog builder, part A: Bulbapedia track lists into a draft manifest. Decisions:
    - Scope: mainline Gen 1-9, including remakes and both Legends games; no spin-offs.
    - Games come from a hand-written, committed games file (`pipeline/data/games.json`: name, shortName, color, generation, platform, family, and later the YouTube playlists per game). Claude drafts colors (Bulbapedia's version colors) and short names; the user reviews them. Bulbapedia supplies only tracks.
    - Track lists come from Bulbapedia's soundtrack album pages, selected per family as page + disc + optional CD number range in the games file. Games without an album of their own: Emerald and Platinum come from B2W2 Disc 4, Yellow from LGPE Disc 3, GSC from a hand-copied Gold/Silver/Crystal game-rip track list in `pipeline/data/tracklists/gsc.tsv` (HGSS Disc 3's GB Sounds versions of HGSS-only songs are HGSS tracks titled "… (GB Sounds)"), BDSP comes from a hand-copied track list in `pipeline/data/tracklists/bdsp.tsv` (a track list can name such a file instead of a page). USUM-only tracks come from a hand-supplied list as override extras. Gen 1 is Red, Blue and Yellow (no Japanese Green).
    - Track ids are `<family>-<title-slug>`. Since step 19 the slug is of the final title, and ids freeze at the first real deploy; after that a corrected title changes `title`, never `id`.
    - Families: SM and USUM start as one family; Part A reports shared vs. exclusive track counts per family, and the user confirms or splits SM/USUM (and any other edge case) before the catalog ships. Confirmed: SM and USUM stay one family (`sm`, label "SMUSUM"), since 133 of 190 tracks are shared.
    - BW and B2W2 are one family, `bw` (label "BWB2W2"), like SM and USUM (revised in step 17; they started as separate families). B2W2 plays many BW tracks unchanged (returning cities and routes, generic themes), and neither its album nor any found track list lists them, so as separate families a reused track could only be repeated as a duplicate, breaking one track per piece of audio. As one family, a reused track is one BW track whose `games` override adds Black 2 and White 2. Each album's discs carry their games (BW's Black and White, B2W2's Black 2 and White 2). The 12 titles on both albums are all different versions, so each is split: the BW side is titled "… (Black & White)" and the split-off B2W2 side "… (Black 2 & White 2)" (ids `bw-<slug>` and `bw-<slug>-b2w2`). "BW", "B2W2" and "BW2" are aliases of the family, since its label no longer names either pair; the score's game evidence is per family, so a BW upload counts as the right game for a B2W2 track, as within SMUSUM, and playlists tagged per pair keep candidates apart. Reused tracks are tagged as they are found: by inference from the sequel-exclusive list, by listening, and exactly in step 20 (a B2W2 sequence identical to a BW one in the ROMs' sound archives is reused). Z-A is different: its Disc 5 reuses older games' themes, which belong to their original families, so it stays skipped.
    - Same title within a family merges into one shared track; rearranged versions are split via override.
    - Jingles and fanfares are excluded (a title list, plus 15 s or shorter, since the album pages list durations); an override can bring one back. Where a page lists no durations (Z-A), `pipeline/data/durations.json` supplies them from another listing of the same album (VGMdb, copied by hand).
    - Hand corrections (title, category, games, merge, split, parts, exclude, extra tracks) live in a committed overrides file (`pipeline/data/overrides.json`) keyed by track id, reapplied on every build. An override for a track that doesn't exist fails the build. Never hand-edit the generated manifest.
    - The builder's output replaces the seed manifest. Seed ids that change only affect the dev install: clear app data once, no `replaces`. Step 8's local test file is a real track's audio (see step 17), not the seed's test tone.
    - Bulbapedia wikitext comes from the MediaWiki API, cached in `pipeline/out/` (gitignored), parsed with mwparserfromhell. A few trimmed pages are committed under `pipeline/tests/` so pytest runs offline.
    - Until Part B, tracks have no stream sources, so the draft (`pipeline/out/draft.json`, with each track's duration and Bulbapedia origins) is not yet a valid manifest; don't overwrite `catalog/manifest.json` in this step.

    - [x] B2: the review tool, a local page (stdlib `http.server`) where the user decides the final track list. Everything the user does by hand for the catalog happens here, and every decision is written to a committed file under `pipeline/data/`, so reruns keep it. Two sessions: B2a (the tool and track review), then B2b (playlists).
    - Left of step 17 when B2 merged (PR #10): reviewing SV (68 of 180 matched, playlists in place) and SM/USUM (no playlist yet), finished alongside step 18 with its renaming and notes in the tool. Step 17 is checked off when both are in the manifest.

Each track's first source is its slice of one full-album upload (SV `VzG7oP2oSUQ`, SM/USUM `TO6iwQsLj4k`), from timestamps the user pasted; earlier picks stay behind it as fallbacks. Both videos are the official Super Music Collections, so chapters map to the track lists by position (row n = chapter n, lengths checked within 3 s), not by title: the uploaders' chapter names are fan translations, and the official titles and ids stay.         - Playlists: which families and games have none or too few matches; search YouTube for playlists from the page, preview their entries against the family's tracks, then add one (with its games and optional range) to the games file's `youtube` block or remove one.
        - Tracks: per needs-review track, embedded players for its best candidates with their scores and reasons; accept or reject writes `streams` overrides. Matched tracks can be reopened to replace a wrong auto-accept; an unmatched track can get a video by search or a pasted video ID.
        - No flags in the review tool. Auto-matching is good enough, and the tool's reject, accept, paste and remove already fix any track it shows. Wrong matches that remain are found by listening, so flagging moves to the app (see the in-app flags candidate).

    B2a decisions:
    - The tool runs with `uv run python -m vgmixr_pipeline.catalog.review` (`--cached-only` never asks YouTube) on 127.0.0.1:8765, single-threaded so writes never overlap. Writes need a JSON body and a local Host header, so another site open in the browser can't post to it. The page is plain HTML/JS/CSS; YouTube's IFrame API is its only external script. Players load on click, play from `startMs` to `endMs`, and a video that can't be embedded shows the error and a YouTube link; it can still be accepted.
    - At startup the tool matches every track from the YouTube cache with the builder's code (about 10 s) instead of reading `candidates.json`, which goes stale when overrides change after a build. A decision rematches only its track. Rebuild runs the whole builder with `--cached-only`.
    - Matching never asks YouTube. Only a search or a pasted-video lookup does, at most every 5 s. YouTube's bot check raises `YouTubeBlocked`; the tool then uses the cache for 30 minutes (the page shows until when, with a Try again button). A pasted link is reduced to its video id; only ids are stored.
    - The data files have one canonical format (`catalog/jsonfmt.py`), the original hand style: one entry per line, a blank line between families, and in overrides.json a note on a continuation line when an entry passes 140 chars. A test keeps the committed files in it (`uv run python -m vgmixr_pipeline.catalog.jsonfmt` rewrites them), so a tool edit is a one-line diff. overrides.json's track entries were regrouped by family once. A new override goes after the last one of its family; `streams` goes before `note`.
    - Every write is validated with the builder's models (plus: the track is in the draft) before it is written, through a temp file; an invalid edit is refused and nothing is written. Clearing a decision removes `streams`, and an override left empty.
    - A track with no usable stream can be removed from the page: that writes `exclude: true`, the builder's existing override. Until the next Rebuild it shows under Removed with a Restore button; restoring a short track that was kept on purpose writes `exclude: false` again so the jingle rule doesn't drop it. After a Rebuild it's gone from the tool; undoing it is a hand edit.

    B2b decisions:
    - The page has a Playlists mode. Families are ranked by gaps: no playlist first, then by the share of tracks without sources. Each game shows its playlist count and its review/unmatched tracks, which surfaces gaps like Yellow, Emerald, Platinum and USUM-only tracks.
    - Playlist search uses YouTube's results page with the playlists filter (yt-dlp has no playlist-search prefix). It is capped at 15 results with `playlistend`, since the page otherwise keeps paginating. Results are cached under `playlist-search/`. A flat playlist search lists only id, title and channel, with no entry count. The count shows once the playlist itself is cached.
    - A preview rematches the playlist's families with it added (or removed) and writes nothing. It matches from the cache only, with cached search results still counting, so before and after compare like with like. It shows the matched/review/unmatched counts before and after, the tracks that would change (✎ marks a track with a hand decision; sources are shown as accepted or auto), and each entry next to the track it would match. Entries outside first..last are dimmed.
    - A playlist is fetched live once, through the same spacing and block fallback as searches. Later previews, the add and every rematch read the cache. Adding a playlist never searches for the family's leftover tracks: they are searched one at a time from the track page.
    - Adding writes one line to games.json through the same validated canonical write as overrides. The new entry goes after the playlists of its first game's family (families in games-file order). The same playlist may be listed again with other games or another range, for an album holding several families' tracks, but never twice the same way. Removal names the entry's index and playlist id, so a stale page can't remove the wrong entry. Either one rematches the playlist's families. A playlist whose games span families previews and rematches all of them.
    - Hand decisions are unaffected: accepted slices stay first and rejected videos stay out, whatever the playlists are. Removing a playlist keeps a hand-accepted video from it, since decisions are stored by video id.
    - An album track that plays several pieces in a row (BW's route themes: one season per cycle, e.g. "Route 2 (Spring/Summer)") is split by a `parts` override into consecutive tracks in its place. Each part's id comes from its title, it keeps the track's games, and its length is its own or an equal share of the whole. Parts take their own overrides; the split track's override holds only `parts` and a note. A part never auto-accepts a video over 1.5× its length (an upload of the whole album track, which plays the other parts too); such a video goes to review, where the part gets a slice of it. Undella Town stays two tracks (Summer, and Autumn/Winter/Spring), since the latter is one piece used for three seasons.
    - A track merged from pieces played back to back (an opening and its title screen, via `mergeInto`, and any track split off such a track) is never auto-matched: its best videos go to review. Length can't tell a whole-sequence upload from a one-piece one, since the title screen is a loop that runs as long as the uploader let it. Hand-accepted videos stay. Merged openings use whole-sequence uploads; if joining ROM pieces into one local file proves too hard in step 20, they stay stream-only.
    - Album videos (`youtube.albums`, chapters as slices) stay hand-edited: none are in use, and playlists cover today's gaps. If one is needed later, the same preview works with `video()` chapters.

    Decisions:
    - Every track gets stream sources, including tracks that will later get local files (local sources go in front of them).
    - YouTube access via yt-dlp (no API key or quota). Playlists first: per-game playlists from the games file, matched by title within the right game. Search (top ~10 results) only for leftovers. Album videos with description timestamps become `startMs`/`endMs` as a last resort.
    - Confidence is a hand-tuned 0-1 score from title similarity (after stripping noise), right-game evidence (a wrong-game hit such as a remake is heavily penalized), red flags (remix, cover, orchestra, extended, hour-long, implausible duration), source trust and playlist position. Weights are tuned against a committed hand-labeled set as a pytest fixture.
    - High score: auto-accept the top 2-3 as sources, best first. Middle: review tool, with decisions saved to the overrides file so reruns don't ask again. No acceptable match: the track is left out of the manifest (at least one source is required) and listed in a report.
    - The app keeps ignoring `confidence`; wrong-but-playable matches are fixed by override and rebuild.
    - Playlists, album videos and extra game-name aliases live in a `youtube` block of the games file; games stay plain manifest games. A family can have several playlists, and a playlist's `games` can span families (B2W2's album holds Emerald and Platinum tracks); `first`/`last` limit it to a range of positions. Good playlists, best first: official album uploads, complete game rips (one video per track, titles close to the official ones), album videos with timestamps.
    - Score: `title × (0.65 + 0.15·evidence + 0.10·trust + 0.10·position)`, times 0.15 for a wrong game and 0.5 per red flag, different number or variant (region, day/night) only the video names, and 0.4 for a length outside 0.4-3.5× the album's. The title gates the rest, so a right-game playlist entry with another track's title isn't reviewed. Words shared by most of a playlist's titles are noise. Game names count anywhere when distinctive (Omega Ruby, HeartGold, ORAS) and only right after "Pokémon" when they're plain words (Gold, Moon). Accept at 0.80 or more, review from 0.50. Red flags include covers, remixes, extended or hour-long uploads, demakes, transcriptions, MIDIs, edits without melody, dubs, guides and joke-rip channels (SiIvaGunner).
    - The labeled set (`pipeline/tests/data/youtube/labeled.json`) is 151 real candidates from rby, gsc, rse, frlg, hgss and oras, 70 good and 81 bad, sampled toward remakes, red flags and near-threshold scores; rows that need listening to judge were left out. Its test requires no bad candidate accepted, at least 75% of good ones accepted (84% today) and at most 10% rejected.
    - A needs-review track stays out of the manifest until it has a decision. Decisions are a `streams` override: `accept` (slices, first, with confidence 1.0; auto-accepted ones fill up to 3) and `reject` (video ids, never used again).
    - Every track is matched, also one with a local file. A `local` override puts hand-copied files in front of a track's streams. The seed's test tone is gone: Route 101 (RSE) has a local file, its stream's audio downloaded with yt-dlp as m4a, copied by hand to `files/music/rse/route-101.m4a`.
    - The first real manifest (B1) covers the six families with playlists so far (519 tracks); the rest are listed as unmatched until their playlists are added. `--cached-only` builds from cached YouTube responses without any request.
    - The manifest is written only if it validates, and keeps its `generatedAt` when nothing else changed, so a rerun shows no diff and the app doesn't re-import.
18. [x] Review tool: hand-set track order, renaming and notes. No source can say where they go (an album lists only its own game), so the user sets the order.

    - Storage: one ordered id list per family, one id per line (a move is a two-line diff), in the canonical format. A drag rewrites the list. A track missing from the list (a new track list, a split) goes right after the listed track that precedes it in track-list order. An id that's no longer a track fails the build, naming it, as a stale override does. The ids are source keys, like the overrides', so step 19 doesn't touch the file. Relative `after` placements were the alternative: sparse, but a drag becomes rules that are hard to read back.
    - Rename a track from its page in the review tool: writes a `title` override (no schema change), and the list, the track page and the default search query use the new name at once. Renaming pins the track's current videos first: its auto-picked videos are saved as accepted ones, in order, so a rename never drops or reorders a source (matching scores titles, and cached searches are keyed by the old title). They show as accepted rather than auto afterwards. Rejected alternative: scoring candidates against both the album title and the new one, which would change the sources of every already renamed track on the next build.
    - Notes on every track, edited from its page in the review tool: the override's existing `note` (one field for every hand-written note, e.g. "also plays in X", "a remix of Y"), saved through the same validated write. Notes stay in the pipeline's data; showing them in the app later would add an optional manifest field.
    - One order per family for every game, decided: BWB2W2 keeps a single order, so a White 2 filter lists the BW tracks B2W2 reuses in BW's story order. Per-game order (a schema change) isn't needed for now.
    - The order lives in `pipeline/data/order.json` (family id -> ids; a missing file or family means track-list order). The build checks ids against the tracks before exclusion, so a removed track may stay listed and keeps its place if restored.
    - Matching keeps the track-list position: the draft records it as `listOrder`, and the score's playlist-position evidence uses it, since playlists follow the albums. `order` is the hand-set order, for the manifest and the tool, so a drag never changes a match.
    - A drag moves a track right before or after the row it is dropped on, so it works from a filtered tab too; the tool then writes the family's whole list.
    - A rename refuses another track's title in the same family (ignoring case), since tracks that share a name need their version qualifiers and step 19 fails on duplicates. Titles and notes are one line; whitespace is collapsed.
19. [x] Catalog ids from final titles. Today a track id is the family plus a slug of the source's title (Bulbapedia's or a KHInsider list's), so a corrected title, merge or split leaves an id that no longer matches the track (e.g. `dppt-canalave-city` for "Canalave City (Day)", `dppt-title-screen-pokemon-platinum` for "Opening Movie (Platinum)"). Nothing outside the pipeline depends on ids before the first real deploy, so they should read well.
    - Split the id's two jobs. The source key (today's id) stays the key of overrides, review decisions and the review tool, so `overrides.json` doesn't change. The catalog id, the one the manifest and the app see, is the family plus a slug of the track's final title, after title overrides, merges and splits, computed when the manifest is written.
    - Two tracks of a family with the same final title fail the build, naming both.
    - The check compares catalog ids, not raw titles, so titles that slug alike ("Pokémon Center" and "Pokemon Center", "&" and "and") collide too. Only kept tracks count: an excluded track never ships. The review tool's rename refuses such a title too, so it can't write a rename the build rejects.
    - An extra's hand-written `id` is a source key like any other, so it keys overrides but the extra ships under its title's slug (e.g. `sm-title-screen-usum` ships as `sm-title-screen-ultra-sun-and-ultra-moon`).

## Candidates (not scheduled)
- Local file playback: play `local` sources from `files/music/` before streams, skipping missing files, with the source order of the manifest (local files, then a cached download, then streams). Step 8 plays streams only, so this comes with the first real local files: step 20's ROM rips, or the local files from full-album slices (below).
- Accent color setting: the user picks the app's one accent color in settings. The theme already takes the accent as a single parameter (step 7a), so this is a stored setting passed into it. As in Shuttle, the choice is a handful of saturated colors (Shuttle offers blue, cyan, green, orange, magenta and red), not any color: the accent tints the playing row at low alpha and colors spinners and the selected tab, which only work for saturated colors.
- Standardize track titles across all games with one consistent format. Titles come from several sources (Bulbapedia albums, KHInsider rips, hand-supplied lists), so the same idea is written differently: "Trainers' Eyes Meet (…)" vs "A Trainer Appears (…)", "Battle! (Trainer Battle)" vs "Battle! (Trainer)", "(Pokémon Black)" vs "(Black 2)", "/" vs " - " between names, acronym casing ("Gts", "(Pwt)"), curly vs straight apostrophes. Likely a normalization step in the builder plus a short style guide, with `title` overrides for the rest. Track ids derive from titles and freeze once published, so do this before the catalog ships if the ids should follow the standard titles; afterwards it can only change `title`.
- Opening movies, for every game: merge each game's opening pieces (logo, opening, title screen) into one "Opening Movie" track, qualified by versions where a family has several ("Opening Movie (Red & Blue)", "Opening Movie (Yellow)"). Done so far: RBY, GSC, RSE, FRLG, DPPt, HGSS, BW/B2W2, XY, ORAS, LGPE, SwSh (its title screen is the opening, renamed), BDSP, PLA and Z-A. Still to do: SM and SV. A merged track needs an upload of the whole sequence (an upload of one piece plays only that piece), picked by hand: merged tracks are never auto-matched.
- In-app editing of a track's category, and of loop points on `local` sources. Edits are user data in Room, like favorites: a category edit is keyed by track id, a loop edit by local `path`. They override the manifest values and survive re-imports. Their relationship to the pipeline's overrides file (for example, exporting them back as overrides) is still to be decided. Finalize the category list before making category edits, so stored edits never need migrating to new names.
- Seamless looping for `stream` sources (the goal: intro → loop → loop → fade, so every track plays at least two cycles), built together with v2 local looping, since both need the same player code. Most uploads are about one cycle (matched videos are 0.87-1.03× the album length per family), but they usually run a few seconds into the second cycle. That carryover repeats the start of the loop, so the pipeline can find both loop points from the upload alone by matching it against the earlier audio (as loop finders like PyMusicLooper do), without a ROM rip. Start with a detection spike on a few dozen matched tracks, listened to by hand. Costs: downloading every stream's audio (cached and spaced like other YouTube requests), new dependencies (likely numpy and a decoder; ffmpeg isn't installed), and a review-tool check of detected points, since uploads that fade during the carryover or have none fall back to playing once. Loop points are per video, keyed by `(videoId, startMs, endMs)`, accurate to milliseconds rather than samples. Loops play only from the cached download (a live stream would rebuffer on every seek back to `introEnd`); verify that lossy Opus/AAC seams are gapless first. Allowing `loop` on `stream` sources removes the `stream-loop-present` error, so it bumps `schemaVersion`. A cruder interim that needs no schema change: store only the detected loop end as the slice's `endMs` and play the whole slice twice (intro → loop → intro → loop), using Media3's repeat and step 10's clipping.
- In-app flags: a "flag" button on now-playing that takes a free-text note ("wrong song", "intro cut off", "this is the XY version", "missing the Delta Episode tracks"), with no kinds or categories. The app attaches the context itself: track id, the playing source's identity (`videoId`, `startMs`, `endMs`, or a local `path`), the playback position, the time and the manifest's `generatedAt` (so a flag on an old build can be recognized as fixed). Flags are user data in Room, like favorites. An "Export flags" action shares them as a JSON file that the user saves into the repo; a Claude Code session reads them, maps each to a fix (reject or replace a video in the review tool, a title, merge or split override, an extra, a playlist change), rebuilds, and clears the handled ones. Replacing wrong audio still needs the user's ears in the review tool. A flagged source keeps playing until the next build: free text can't tell the app to skip it. Fits after step 10 (now-playing shows which source plays), e.g. alongside step 11 or 12, which touch the same Room setup. Decide together with the in-app category and loop edits how app data reaches the pipeline.
- Local files from full-album slices: a one-time pipeline step that downloads each full-album video once (yt-dlp), cuts every track's accepted album slice into its own file with ffmpeg (stream copy, no re-encode: cuts land within a codec frame, about 20 ms), names it by track id under `pipeline/out/` (never committed), and writes the `local` overrides that put the files in front of the streams. The user copies the files into the app's `files/music/` by hand, as with other local files. Cutting the accepted slices rather than raw chapters keeps every hand correction (seams, merged openings, season parts). It mostly removes the caching question for these families (local files play first) and suits SV, which has no ROM-rip plan; SM/USUM's 3DS rips (step 20) would later take over. Needs ffmpeg, a new tool: ask before installing it. About 60-70 MB per hour of album at YouTube's best audio format, 0.5-0.9 GB for both albums.
